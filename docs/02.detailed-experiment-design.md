# Thiết kế chi tiết từng thí nghiệm

## 1. SQL Query Optimization

Module nên dùng `GET /orders` và `GET /orders/:id`

Đây là lực chọn tốt vì bạn có thể tạo dataset lớn mà không cần thêm nghiệp vụ phức tạp

### Thí nghiệm A. Tối ưu danh sách đơn hàng

Truy vấn danh sách orders, JOIN với order items khi cần, lọc theo trạng thái và sắp xếp theo thời gian tạo.

#### Các biến thể

1. Không có index phù hợp
2. Thêm index cho các cộc lọc và sắp xếp phù hợp với query thực tế.
3. So sánh offset pagination và keyset pagination khi số trang tăng.

#### Số liệu cần lấy

- Execution time và actual rows
- Shared buffer hits/reads.
- Loại scan và join được PostgresSQL chọn.
- p95 latency nếu benchmark qua API.

### Thí nghiệm B. Tối ưu truy vấn checkout

Dùng truy vấn đọc variant theo danh sách ID hoặc kiểm tra tồn kho trước checkout. So sánh execution plan trước và sau khi tối ưu.

Tuy nhiên, hãy giữ nguyên logic nghiệp vụ giữa các lần đo. Nếu bạn thay cả index, SQL và cách transaction hoạt động cùng lúc, sẽ khó xác định nguyên nhân cải thiện.

**Lưu ý**: `EXPLAIN ANALYZE` thực thi truy vấn thực sự. Với câu lệnh ghi dữ liệu, chỉ chạy trong môi trường test có thể rollback an toàn;không thử tùy tiện trên dữ liệu thật.

## 2. Idempotency

Module nên dùng: `POST /checkout`, với bảng `idempotency_keys`.

Bạn nên có bốn kịch bản:

| Kịch bản                              | Hành vi cần xác minh                                         |
| ------------------------------------- | ------------------------------------------------------------ |
| Cùng key, cùng payload, gửi tuần tự   | Không tạo đơn thứ hai                                        |
| Cùng key, cùng payload, gửi đồng thời | Chỉ một thao tác tạo đơn được thực hiện                      |
| Cùng key, payload khác                | Từ chối hoặc xử lý theo contract đã định nghĩa               |
| Transaction thất bại rồi retry        | Không để key ở trạng thái sai hoặc mất khả năng retry hợp lệ |

### Các metric cần ghi

- `order_created`: số đơn được tạo.
- `stock_decrement_operations`: số lần trừ kho thực sự.
- `duplicate_orders`: số đơn trùng.
- `idempotency_conflicts`: số request bị từ chối vì key/payload không khớp.
- `p95_latency_ms`: độ trễ khi có retry hoặc cạnh tranh key.

Ví dụ, bạn gửi 100 request đồng thời vào cùng một key và payload. Nếu thiết kế của bạn yêu cầu một thao tác checkout thành công, kết quả kỳ vọng là một order, stock chỉ bị trừ một lần và các response còn lại tuân theo contract idempotency.

Đừng chỉ kiểm tra HTTP status. Hãy truy vấn database sau khi test để xác minh trạng thái thực tế.
